# Cline Kanban Enhancement — Product Requirements & Acceptance Criteria

## 1. 任务目标

基于现有开源项目 [cline/kanban](https://github.com/cline/kanban) 进行增强开发。

目标是在**尽可能保留现有产品 UI、交互体验、Agent Session、任务调度、看板和 Review 能力**的前提下，解决以下问题：

1. Project 创建强依赖 Git Repository。
2. 无法将普通本地文件夹或 Google `repo` 多仓工作区作为一个 Project。
3. Agent 后端支持有限，缺少 Pi，并且部分已注册 Agent 无法正常启动。
4. Claude Code 强制采用 Auto Permission Mode，缺少用户自主选择权限模式的能力。
5. 任务执行缺乏统一、可配置的 Direct Workspace / Isolated Workspace 模型。
6. 当前 Git Worktree 与 Diff Review 模型无法完整覆盖非 Git 项目和 Google `repo` 多仓目录。

本项目是对现有 Cline Kanban 的**渐进式增强**，不是重写产品。

### 核心原则

- Folder-first，Git-optional。
- Project 与 Git Repository 解耦。
- Agent Backend 可扩展、可配置。
- Agent 权限由用户明确控制。
- Task 可以独立选择执行模式。
- 兼容普通 Git、Google `repo` 多仓和完全无 Git 的文件夹。
- 保留原有功能与用户数据。
- 尽可能降低对上游源码的侵入性，便于后续同步更新。

## 2. 功能需求

### FR-01：任意本地目录作为 Project

**优先级：P0**

用户应能够从本地文件系统选择任意已有的、可访问的目录作为 Project Root。

支持以下目录类型：

- 普通 Git Repository。
- Git Worktree。
- Google `repo` 管理的多仓工作区根目录。
- 包含多个独立 Git Repository 的父目录。
- 完全没有 Git 元数据的普通文件夹。
- Git 与非 Git 文件混合的 Workspace。

#### 需求

1. 不得以是否存在 `.git` 作为 Project 创建的必要条件。
2. 不得要求 Project 关联 GitHub、GitLab 或其他远程 Git 服务。
3. 不得为了创建 Project 自动执行 `git init`。
4. 不得强制创建初始 Git Commit。
5. Project Root 必须保留用户指定的目录语义，不应自动替换为某个子 Git Repository 的根目录。
6. 不得因 Git Discovery 失败而阻止 Project 创建、Board 操作或 Agent 启动。
7. 现有 Git Repository 项目继续保留完整能力。
8. 支持 Project 重启后的恢复、切换、删除和路径校验。
9. 不得因为 Project 包含多个 Git Repository，就将其强制拆分为多个 Project。

#### 验收标准

- AC-01.1：选择普通非 Git 文件夹，可以成功创建 Project。
- AC-01.2：选择 Google `repo` 顶层目录，可以成功创建 Project。
- AC-01.3：选择包含多个 Git 仓库的父目录，可以成功创建一个 Project。
- AC-01.4：上述目录创建 Project 后，均可使用看板、创建任务和启动 Agent。
- AC-01.5：创建 Project 不会修改原目录中的 Git 元数据。
- AC-01.6：重启应用后，Project 仍能正常加载。
- AC-01.7：现有普通 Git Project 的功能不发生回归。

### FR-02：Workspace 类型自动识别

**优先级：P0**

Project 创建成功后，可以进行 Repository Discovery，但 Discovery 只用于启用附加能力，不用于决定 Project 是否有效。

应支持以下类型：

- `none`：普通文件夹。
- `git`：单 Git Repository。
- `multi-git`：包含多个独立 Git 仓库。
- `google-repo`：Google `repo` 管理的多仓工作区。

#### 需求

1. 自动识别 Workspace 类型。
2. 检测失败不影响 Project 的基本功能。
3. 识别结果可在 Project Settings 中查看。
4. Google `repo` 优先使用其 Manifest 与项目列表识别子仓库。
5. 支持嵌套目录、Git Worktree 及 `.git` 文件形式的 Git 元数据。
6. 允许用户刷新检测结果。
7. 类型识别错误时，应允许用户手动覆盖或禁用 Git 集成。
8. Repository Discovery 不能改变 Project Root。

#### 验收标准

- AC-02.1：普通文件夹正确识别为 `none`。
- AC-02.2：单仓库目录正确识别为 `git`。
- AC-02.3：多仓库父目录正确识别为 `multi-git`。
- AC-02.4：Google `repo` 根目录正确识别为 `google-repo`。
- AC-02.5：检测失败时任务管理和 Direct Agent Execution 仍然可用。

### FR-03：Direct Workspace Execution

**优先级：P0**

允许 Agent 直接在 Project Root 中执行任务。

#### 需求

1. Agent 的工作目录为 Project Root。
2. 无需 Git Worktree。
3. 无需 Git Branch。
4. 不要求 Project Root 是 Git Repository。
5. Agent 可以访问 Project Root 下的多个子仓库及普通文件。
6. 所有已支持的 Agent 后端均可使用 Direct Mode。
7. 在 UI 中明确显示 Direct Mode。
8. Direct Mode 不得自动清理、重置或覆盖用户已有文件。
9. 默认防止同一物理工作区中的多个写入任务发生冲突。
10. Direct Mode 的修改已经作用于源目录，不应提供误导性的二次 Merge 操作。

#### 验收标准

- AC-03.1：普通非 Git 文件夹可以启动 Agent 并修改文件。
- AC-03.2：Google `repo` Root 可以启动 Agent。
- AC-03.3：Agent 能够在单个任务中修改多个子 Git Repository。
- AC-03.4：任务结束后修改保留在原 Workspace。
- AC-03.5：取消或删除任务不会自动丢弃用户文件修改。
- AC-03.6：同一目录的并发写入冲突受到调度保护。
- AC-03.7：已有单 Git 仓库的 Direct Mode 正常运行。

### FR-04：Isolated Workspace Execution

**优先级：P1**

允许用户对单个任务选择隔离执行，避免 Agent 修改原始工作目录。

#### 需求

1. 每个 Isolated Task 拥有独立 Workspace。
2. Agent 的工作目录指向隔离环境。
3. Agent 修改不得直接影响源 Workspace。
4. 普通 Git 项目保留现有 Git Worktree 能力。
5. 非 Git 项目允许创建独立目录快照。
6. Google `repo` 项目支持完整多仓目录结构隔离。
7. 隔离环境必须保持工作区内部相对路径关系。
8. 不得存在意外指向原 Workspace 的可写 Git 元数据路径或符号链接。
9. 支持多个 Isolated Task 并行运行。
10. 支持查看、保留和清理隔离 Workspace。
11. 隔离创建失败时，应提示用户，不得静默退化为 Direct Mode。
12. 对大型工作区应尽可能采用高效、可配置的隔离策略。
13. 隔离后的 Git 操作不得意外修改源仓库的 Branch、Index 或 Worktree 状态。

#### 验收标准

- AC-04.1：普通 Git 项目的原有 Worktree 机制不回归。
- AC-04.2：非 Git 文件夹可以通过 Isolated Mode 执行任务。
- AC-04.3：Google `repo` 多仓项目可以创建独立任务目录。
- AC-04.4：在隔离目录修改子仓库文件不会影响源目录。
- AC-04.5：不同隔离任务可以并行修改同名文件而不相互干扰。
- AC-04.6：隔离环境异常时不会误删源 Workspace。
- AC-04.7：任务可以保留隔离现场用于排查或继续执行。
- AC-04.8：隔离模式不会擅自复制或暴露凭证、密钥等敏感文件。
- AC-04.9：隔离环境创建完成前不会启动 Agent。

### FR-05：任务级执行模式

**优先级：P0**

每张任务卡片都可以配置 Workspace Execution Mode。

支持：

- `direct`
- `isolated`

#### 需求

1. 创建任务时可选择执行模式。
2. Project 可设置默认执行模式。
3. Task 可以覆盖 Project 默认值。
4. Task UI 明确展示当前模式。
5. 任务尚未运行时允许修改模式。
6. 任务运行期间不得直接切换到另一个 Workspace。
7. 重试任务必须明确使用哪种执行模式。
8. 执行模式信息应持久保存。
9. 如果某模式暂不可用，显示明确原因及建议，不进行静默转换。

#### 验收标准

- AC-05.1：同一 Project 可以同时拥有 Direct 与 Isolated 类型任务。
- AC-05.2：用户可在创建任务时选择模式。
- AC-05.3：任务重启后配置仍然存在。
- AC-05.4：运行中的任务不能因切换模式造成工作目录变化。
- AC-05.5：不同模式对应正确的文件生命周期与 Review 行为。

### FR-06：多 Agent Backend

**优先级：P0**

至少支持：

- Claude Code
- OpenAI Codex
- Pi Coding Agent
- OpenCode

同时保留原有 Agent 后端。

#### 需求

1. 用户可以在任务级别选择 Agent。
2. 每个 Agent 可以使用不同的模型。
3. 支持检测本地已安装的 Agent CLI。
4. 未安装的 Agent 应显示正确的安装提示。
5. Agent 应使用任务对应 Workspace 的工作目录。
6. Agent 启动参数可以按 Agent 类型独立配置。
7. 支持用户可配置的额外 CLI 参数。
8. 不得强制所有 Agent 使用同一种权限或自主执行策略。
9. Agent Session 支持实时终端输出。
10. 支持任务中断、继续和重新执行；无法原生恢复 Session 的后端应明确告知。
11. 保留原有 Agent Hooks、状态更新及终端功能。
12. Agent 支持能力应按后端显式声明，例如交互式 TUI、结构化事件、恢复、权限请求和模型选择。
13. 不得因为一个 Agent 不支持特定 Hook 而阻止其基本运行。

#### 验收标准

- AC-06.1：可以创建 Claude Code 任务并成功启动。
- AC-06.2：可以创建 Codex 任务并成功启动。
- AC-06.3：可以创建 Pi 任务并成功启动。
- AC-06.4：可以创建 OpenCode 任务并成功启动。
- AC-06.5：四种 Agent 均支持 Direct Mode。
- AC-06.6：支持 Isolated Mode 的 Agent 能在对应隔离目录运行。
- AC-06.7：不同任务可以选择不同 Agent。
- AC-06.8：执行期间可查看输出，并正确停止 Session。
- AC-06.9：缺少某个 Agent CLI 时，不影响其他 Agent。
- AC-06.10：现有 Agent 后端无功能回归。

### FR-07：Agent 权限模式自由配置

**优先级：P0**

取消 Claude Code 强制启用 Auto Mode 的设计。

#### 需求

1. 用户可以为 Claude Code 选择权限模式。
2. 不应自动追加 `--permission-mode auto`，除非用户明确选择 Auto Mode。
3. 不应无条件设置 `CLAUDE_CODE_ENABLE_AUTO_MODE=1`。
4. 应支持 Claude CLI 当前版本实际提供的权限模式。
5. 用户可以选择采用 CLI 默认权限行为。
6. 权限模式可以配置 Project 默认值与 Task 覆盖值。
7. 支持交互式权限审批。
8. 当 Agent 等待权限时，看板应标记为 `Needs Attention`，而不是误判为任务完成。
9. 用户完成审批后，任务能够继续。
10. 自主执行模式与权限控制必须相互独立。
11. 不应静默启用绕过权限检查的选项。
12. 对于其他 Agent，也应提供后端对应的权限配置方式。

#### 验收标准

- AC-07.1：Claude Code 可以在 Default Mode 下启动。
- AC-07.2：Claude Code 可以在 Plan Mode 下启动。
- AC-07.3：Claude Code 可以在受支持的其他权限模式下启动。
- AC-07.4：默认模式不会被隐式覆盖成 Auto。
- AC-07.5：用户能够在终端或支持的审批界面处理权限请求。
- AC-07.6：等待权限的任务正确显示需要人工介入。
- AC-07.7：权限请求处理后，Session 可以正常继续。
- AC-07.8：修改权限配置不影响其他 Agent。

### FR-08：Review 与变更追踪

**优先级：P1**

现有 Diff Review 应从强制依赖单 Git 仓库，逐渐扩展为与 Workspace 类型匹配的变更审查能力。

#### 需求

1. 单 Git 项目继续保留现有 Diff Review。
2. Google `repo` 项目能够按子仓库聚合变更。
3. 多 Git 项目能够分别显示各子仓库修改。
4. 非 Git 文件夹应能通过文件快照比较查看任务变更。
5. 支持识别新增、修改、删除文件。
6. 不得把用户原有的未提交修改全部误判为 Agent 产生的修改。
7. Direct Mode 显示当前 Workspace 的任务相关变更。
8. Isolated Mode 显示相对于隔离基线的变更。
9. Isolated Mode 的 Apply 操作必须经用户确认。
10. 应检测源 Workspace 与任务基线之间的冲突。
11. 不得在冲突发生时静默覆盖原文件。
12. 不保证跨多个 Git 仓库天然原子提交；必须对部分失败提供明确反馈与恢复信息。

#### 验收标准

- AC-08.1：原有单仓 Diff Review 正常工作。
- AC-08.2：Google `repo` 项目能显示不同子仓库的文件变化。
- AC-08.3：普通文件夹也能查看任务变更。
- AC-08.4：未跟踪文件可被识别。
- AC-08.5：Isolated 结果不会自动写回源目录。
- AC-08.6：Apply 前会检测冲突并要求确认。
- AC-08.7：发生冲突时用户原始修改不会被无提示覆盖。
- AC-08.8：Review 不会因项目根目录不是 Git 仓库而使整个任务页面崩溃。

### FR-09：现有 UI 和功能兼容性

**优先级：P0**

这不是重新设计 Kanban UI 的项目。

必须保留并尽量复用：

- 原有看板及拖拽交互。
- Task 创建和编辑体验。
- Agent Terminal Panel。
- Session 输出与恢复。
- Task 依赖关系。
- 自动化任务流。
- Review 面板。
- 原有 Git Worktree 与 Git 操作。
- 用户设置、项目设置和已有数据。
- 原有主题与视觉风格。

新增配置必须融入原有交互，而不是建立第二套独立任务系统。

#### 验收标准

- AC-09.1：现有 Git 项目无需迁移即可使用，或可无损自动迁移。
- AC-09.2：原有 Task 数据不丢失。
- AC-09.3：原有支持的 Agent 仍可执行。
- AC-09.4：原有 Git Worktree 流程保持可用。
- AC-09.5：新增选项不会明显破坏当前 UI。
- AC-09.6：现有自动化测试继续通过；因需求变更而调整的测试须明确说明。
- AC-09.7：修改遵循项目当前代码规范与架构。

## 3. 领域模型要求

以下为概念模型，不要求直接照搬为数据库表或 TypeScript 接口。

### 3.1 Project

代表一个由用户选定的本地工作目录。

属性：

- `id`
- `name`
- `rootPath`
- `workspaceType`
- `defaultExecutionMode`
- `defaultAgentId`
- `defaultPermissionPolicy`
- `settings`

约束：

- Project 不依赖 Git Repository 存在。
- 一个 Project 可以包含零个、一个或多个 Git Repository。
- Project Root 是用户指定的工作空间边界。

### 3.2 Repository

代表 Project 内发现的可选版本控制资源。

属性：

- `id`
- `projectId`
- `relativePath`
- `gitRoot`
- `revision`
- `branch`
- `metadata`

约束：

- Repository 不是 Project 的必要组成部分。
- Repository Discovery 失败不应影响任务管理。
- Google `repo` 的各个子仓应作为一个 Project 下的 Repository 集合，而不是自动拆成多个 Project。

### 3.3 Task

代表看板中的工作任务。

属性：

- `id`
- `projectId`
- `title`
- `description`
- `status`
- `agentId`
- `model`
- `permissionPolicy`
- `executionMode`
- `dependencies`
- `createdAt`
- `updatedAt`

约束：

- Agent、权限策略和执行模式可以由 Task 独立指定。
- Task 与 Agent Session 不能简单视为一对一关系。
- 一个 Task 可以有多次执行记录。

### 3.4 Workspace Instance

代表某次 Task Execution 的实际文件系统环境。

属性：

- `id`
- `taskId`
- `mode`
- `sourceRoot`
- `workingDirectory`
- `state`
- `baseline`
- `createdAt`
- `cleanupPolicy`

约束：

- Direct Instance 的工作目录指向源 Project Root。
- Isolated Instance 的工作目录是独立隔离路径。
- 不同 Isolated Instance 之间应有独立的写入空间。
- 清理 Workspace Instance 不得错误删除源 Project。

### 3.5 Agent Backend

代表一种能够执行任务的 Coding Agent。

属性：

- `id`
- `displayName`
- `executable`
- `launchOptions`
- `supportedCapabilities`
- `permissionOptions`
- `modelOptions`
- `sessionCapabilities`

约束：

- Agent Backend 不依赖 Project 是否有 Git。
- 各后端具有独立的参数和权限语义。
- 新增 Agent 不应要求修改 Kanban 核心任务模型。
- 后端能力缺失应优雅降级，而不是冒充支持。

### 3.6 Agent Session / Task Execution

代表一次具体 Agent 运行。

属性：

- `id`
- `taskId`
- `workspaceInstanceId`
- `agentId`
- `model`
- `permissionPolicy`
- `status`
- `startedAt`
- `endedAt`
- `resumeToken`
- `events`
- `exitResult`

约束：

- Session 应保留实际启动配置。
- Session 应能够关联输出和状态事件。
- Task 的状态与 Session 的状态应区分。
- 权限等待与执行完成不能混淆。

### 3.7 Change Set

代表某次执行产生的文件修改集合。

属性：

- `id`
- `workspaceInstanceId`
- `baseline`
- `repositoryChanges`
- `nonGitChanges`
- `reviewStatus`
- `applyStatus`

约束：

- Change Set 可以跨多个 Git 仓库。
- 不要求每次执行都产生 Git Commit。
- Direct 与 Isolated 应具有不同的 Apply 语义。

## 4. 非功能需求

### NFR-01：兼容性

- macOS 为首要支持平台。
- 不应引入强制 GitHub、云账户或外部 SaaS 依赖。
- 不应要求用户重新组织现有本地文件夹。
- 必须兼容 Google `repo` 多仓目录布局。
- 尽量保留现有跨平台实现方式。

### NFR-02：安全性

- 不自动开启高风险权限模式。
- 不自动删除或覆盖用户原有工作文件。
- Direct Mode 采取默认单写者调度策略。
- Isolated Mode 不得意外写入源 Workspace。
- 文件路径、符号链接及 Git 元数据路径必须校验。
- 外部 CLI 参数不得导致命令注入。
- 对未信任目录和高风险操作应有明确提示。

### NFR-03：可维护性

- 优先复用已有组件。
- 尽量减少对上游核心模块的侵入性修改。
- 保持 Agent Adapter 可扩展。
- 将 Workspace 类型与执行模式的处理逻辑解耦。
- 不要为 Google `repo` 创建只适用于某一个目录结构的硬编码规则。
- 保留原有测试与类型检查流程。

### NFR-04：性能

- Project 创建不应强制递归扫描大型代码树中的全部文件。
- Google `repo` Discovery 应尽可能利用已有 Manifest 信息。
- Isolated Workspace 创建过程必须可观察，并支持失败恢复。
- 大型多仓目录不能因为 Diff 扫描而长期阻塞看板 UI。

## 5. 实施优先级和范围

### Milestone 1 — Folder-first Project

**P0，必须首先完成**

实现：

- 任意目录创建 Project。
- Project 与 Git 解耦。
- Workspace 类型识别。
- Direct Workspace Agent Execution。
- 兼容现有单仓 Git 流程。

## 6. 必须覆盖的端到端验收场景

### Scenario A：普通文件夹

```text
~/work/plain-project/
├── main.py
├── config.yaml
└── docs/
```

用户能够创建 Project，选择 Claude Code + Direct + Default Permission Mode，启动任务修改 `main.py`。

预期：成功执行，不要求 Git 初始化。

### Scenario B：Google repo 多仓

```text
~/work/android/
├── .repo/
├── frameworks/base/
├── system/core/
└── packages/apps/Settings/
```

用户将 `~/work/android` 注册为一个 Project。

选择 Codex + Direct，要求修改两个子仓中的文件。

预期：Agent CWD 为 `~/work/android`；两个子仓的修改均被保留与识别；不创建根目录 `.git`。

### Scenario C：Pi Agent

用户在非 Git Project 创建任务，选择 Pi。

预期：可以启动 Pi，接收任务 Prompt，并在看板内查看会话状态及输出。

### Scenario D：Claude 权限审批

用户选择 Claude Code + Default Permission Mode。

Agent 请求写入权限。

预期：Kanban 不将权限请求误判为任务完成；用户能够完成交互式审批，并继续执行同一 Session；系统不会自动替换为 Auto Mode。

### Scenario E：隔离任务

同一 Project 新建两个 Isolated Task，分别选择 Claude Code 和 OpenCode。

预期：两个任务的 Workspace 独立；修改互不干扰；源工作目录保持不变。

### Scenario F：跨仓 Review

一个 Isolated Task 修改：

```text
frameworks/base/
packages/apps/Settings/
docs/
```

预期：Review 能分别展示两个 Git 子仓和普通文件夹的修改，且不会在用户确认前写入源目录。

### Scenario G：原有 Git 功能回归

使用普通 Git Repository 创建 Project，完成原有 Git Worktree → Agent → Diff Review → Commit 流程。

预期：原有体验不发生明显回归。
